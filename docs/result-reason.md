# 결과 추천 이유 설계 — “왜 이 무기인가요?”

- 상태: 기획 확정, 구현 대기
- 최신 방향 반영일: 2026-10-10
- 적용 화면: 와일즈 결과·공유 결과

## 목적

결과 화면에서 1순위 무기가 추천된 이유를 사용자가 이해할 수 있게 설명합니다. 문구는 별도의 성격 유형이나 임의의 무기 소개가 아니라, 실제 추천 계산에 사용한 다섯 축의 불일치와 2순위와의 차이에서 만듭니다.

초기 구현은 다음 원칙을 따릅니다.

- 실행 중 AI나 외부 API를 호출하지 않고 같은 입력에 항상 같은 설명을 만듭니다.
- 추천 순위와 추천 이유는 반드시 같은 축별 불일치 함수를 사용합니다.
- 결과 문구를 시트에 새 열로 저장하지 않습니다. 축별 문장 틀과 선택 규칙은 코드에서 관리합니다.
- 적합도 점수를 확률이나 검사 정확도로 표현하지 않습니다. `85점`을 `85% 확률` 또는 `85% 일치`라고 부르지 않습니다.
- 첫 버전은 **1순위 추천 이유만** 설명합니다. 다른 순위 카드를 눌러 차트·소개·영상을 바꿔도 이 영역은 1순위 설명으로 유지하며, 첫 문장에 1순위 무기 이름을 명시합니다.
- 이 기능은 설명만 추가하며 현재 추천 점수, 순위, 동점 처리와 공유 코드 형식을 바꾸지 않습니다.

## 화면 위치와 구성

결과 화면의 순서는 다음과 같습니다.

1. 1~3순위 무기와 나머지 무기 목록
2. **왜 이 무기인가요?**
3. 선택한 무기의 기준 비교 차트와 표
4. 선택한 무기의 공식 소개 문구와 영상
5. 결과 공유

추천 이유 영역은 다음 네 부분으로 구성합니다. 없는 항목은 빈 자리 없이 생략합니다.

| 부분 | 표시 규칙 | 예시 |
| --- | --- | --- |
| 후보 간격 | 1순위와 2순위의 최종 점수 차이를 짧게 설명 | `건랜스와 대검은 거의 비슷한 후보예요.` |
| 잘 맞는 점 | 1순위의 불일치가 가장 작은 축을 최대 2개 설명 | `한방 성향과 행동을 바꾸는 정도가 취향과 가깝습니다.` |
| 1순위가 된 이유 | 2순위보다 불일치가 더 작은 축을 최대 2개 설명 | `대검보다 한방과 관리 기준에서 더 가까워 1순위가 됐어요.` |
| 낯설 수 있는 점 | 1순위의 가장 큰 불일치가 충분히 클 때 한 가지만 설명 | `원하는 것보다 받아치는 플레이의 비중이 높아 처음에는 낯설 수 있어요.` |

제목은 `왜 이 무기인가요?`로 고정합니다. 제목 아래 첫 문장에서 1순위와 2순위의 이름을 밝힙니다. 카드나 목록에서 다른 무기를 선택했을 때도 이 영역의 내용과 강조 상태를 바꾸지 않습니다. 선택에 따라 바뀌는 영역은 기존의 차트·표·공식 소개·영상뿐입니다.

모바일에서는 모든 내용을 한 열로 배치합니다. 추천 이유를 보기 위해 별도의 클릭이나 펼치기 동작을 요구하지 않습니다.

## 계산에 사용할 값

기호는 [검사 설계](test-design.md)의 추천 공식과 같습니다.

- 사용자 축 점수: `U_a`
- 무기 축 값: `W_a`
- 현재 공식으로 계산한 축별 불일치: `D_a`
- 축별 적합도: `F_a = 100 - D_a`
- 무기 최종 점수: 측정된 축의 `F_a` 평균

추천 이유는 원래 값의 단순 절대 차이가 아니라 **현재 공식으로 보정된 `D_a`**를 사용합니다. 따라서 자유도가 사용자보다 높은 차이는 50%, 복잡도·관리 부담이 사용자보다 낮은 차이는 50%만 반영된 값으로 이유를 고릅니다. 화면 문구의 높음·낮음 방향만 `W_a - U_a`의 부호로 판단합니다.

계산 중에는 반올림하지 않습니다. 동점 비교, 축 선택과 임계값 판정도 원본 실수 값으로 수행합니다.

## 코드 구조

### 1. 축별 점수 상세값

`src/core/recommend.js`의 점수 함수가 순위와 설명에 같은 계산을 제공하도록 확장합니다. 기존 호출부의 `score`와 `maxMismatch`는 유지합니다.

권장 반환 형식은 다음과 같습니다.

```js
{
  score: 85.4,
  maxMismatch: 32,
  axes: {
    attack: {
      user: 73,
      weapon: 80,
      direction: 'higher',
      mismatch: 7,
      fit: 93,
    },
    freedom: {
      user: 21,
      weapon: 35,
      direction: 'higher',
      mismatch: 7,
      fit: 93,
    },
  },
}
```

- `direction`은 무기 값이 사용자 값보다 낮으면 `lower`, 같으면 `equal`, 높으면 `higher`입니다.
- 사용자 점수가 `null`인 미측정 축은 `axes`에 넣지 않고 최종 평균에서도 제외합니다.
- 축 순서가 필요할 때는 `src/core/axes.js`의 `AXIS_IDS` 순서를 사용합니다.
- `rankWeapons`, `recommendWeapons`, `remainingWeapons`의 기존 반환과 정렬 결과는 바꾸지 않습니다.

`scoreWeapon`을 확장하거나 별도의 `scoreWeaponAxes(profile, weapon)`을 만들 수 있습니다. 어느 방식을 택하더라도 축별 불일치 공식을 두 군데에 복사하지 않습니다.

### 2. 추천 이유 모델

새 순수 함수는 `src/core/reason.js`에 둡니다.

```js
buildRecommendationReason(profile, winner, runnerUp)
```

HTML 문자열이 아니라 다음과 같은 표시용 구조를 반환합니다.

```js
{
  winnerId: 'gunlance',
  runnerUpId: 'great_sword',
  scoreGap: 0.9,
  comparisonStatus: 'normal',
  gapLevel: 'close',
  tieReason: null,
  closest: [
    { axis: 'attack', mismatch: 7, band: 'very-close', direction: 'higher' },
    { axis: 'freedom', mismatch: 7, band: 'very-close', direction: 'higher' },
  ],
  advantages: [
    { axis: 'attack', amount: 20, winnerMismatch: 7, runnerMismatch: 27 },
    { axis: 'management', amount: 11.5, winnerMismatch: 14, runnerMismatch: 25.5 },
  ],
  tradeoff: {
    axis: 'counter',
    amount: 25,
    winnerMismatch: 32,
    runnerMismatch: 7,
  },
  caution: {
    axis: 'counter',
    mismatch: 32,
    band: 'far',
    direction: 'higher',
  },
}
```

축별 사용자 문장 틀은 `src/core/reason-copy.js`에 모읍니다. 계산 모듈은 축 ID와 수치만 반환하고, `src/ui/views.js`는 구조화된 모델과 문장 틀을 조합해 마크업을 만듭니다. 사용자 이름·무기 이름 등 데이터에서 온 값은 기존 `escapeHtml`을 거쳐야 합니다.

`src/app.js`는 정상 결과와 공유 결과 모두 `result.weapons[0]`과 `result.weapons[1]`을 이 함수에 전달합니다. 이유 계산 때문에 전체 무기 순위를 다시 정해 공유 링크에 저장된 1~3순위를 바꾸면 안 됩니다.

`comparisonStatus`는 다음 네 값 중 하나입니다.

- `normal`: 1·2순위가 있고 현재 상세 계산에서도 1순위 점수가 더 높음
- `tie`: 현재 상세 계산의 최종 점수가 같음
- `stale`: 공유된 순서는 유지되지만 현재 데이터로 계산하면 저장된 1순위 점수가 2순위보다 낮음
- `missing-runner-up`: 2순위가 없음

## 항목 선택 규칙

조정 가능한 수치는 `src/core/reason.js` 상단의 이름 있는 상수로 모읍니다.

```js
const VERY_CLOSE_MAX = 10;
const CLOSE_MAX = 20;
const CAUTION_MIN = 20;
const COMPARISON_MIN = 5;
const CLOSE_SCORE_GAP = 2;
const MODERATE_SCORE_GAP = 5;
```

### 잘 맞는 점

1순위의 측정된 축을 `mismatch` 오름차순으로 정렬하고 최대 2개를 고릅니다. 같은 값이면 `AXIS_IDS` 순서를 사용합니다.

| 불일치 | 구간 | 표현 강도 |
| --- | --- | --- |
| `0 <= D_a <= 10` | `very-close` | 매우 가까움 |
| `10 < D_a <= 20` | `close` | 가까움 |
| `20 < D_a <= 30` | `some-difference` | 차이가 있음 |
| `D_a > 30` | `far` | 차이가 큼 |

선택된 두 축이 모두 20을 초과하면 ‘잘 맞는 점’이라고 단정하지 않고 소제목을 `상대적으로 가까운 기준`으로 바꿉니다.

### 1순위가 된 이유

각 축에서 다음 값을 구합니다.

```text
advantage_a = runnerUpMismatch_a - winnerMismatch_a
```

양수이면 그 축에서 1순위가 2순위보다 더 가깝습니다. 양수인 축을 큰 순서로 정렬해 최대 2개를 고릅니다. 같은 값이면 `AXIS_IDS` 순서를 사용합니다.

- `advantage_a >= 10`: `특히 더 가까웠습니다`
- `5 <= advantage_a < 10`: `조금 더 가까웠습니다`
- `0 < advantage_a < 5`: `근소하게 더 가까웠습니다`
- 양수인 축이 없으면 축 우위 문장을 만들지 않고 동점 처리 문구를 사용합니다.

최종 점수가 같아 `comparisonStatus`가 `tie`이면 이 항목을 ‘1순위가 된 이유’로 표시하지 않습니다. 아래 동점 문구만 사용하며, 한 축의 우위를 전체 순위를 결정한 이유처럼 설명하지 않습니다.

### 후보 간격과 동점

`scoreGap = winnerScore - runnerUpScore`로 계산합니다.

| 점수 차이 | 문구 규칙 |
| --- | --- |
| `0 < gap < 2` | `<1순위>와 <2순위>는 거의 비슷한 후보예요.` |
| `2 <= gap < 5` | `<2순위>도 가까운 후보지만 <1순위>가 조금 더 잘 맞아요.` |
| `gap >= 5` | `<1순위>가 비교적 뚜렷한 1순위예요.` |

최종 점수가 정확히 같으면 일반 점수 차이 문구를 쓰지 않습니다.

- 최대 단일 축 불일치가 달라 1순위가 정해졌으면 `전체 평균은 같지만, 가장 크게 어긋난 한 기준의 차이가 더 작아 <1순위>가 앞섰어요.`라고 설명합니다.
- 최대 단일 축 불일치도 같아 시트 행 순서로 정해졌으면 `<1순위>와 <2순위>는 계산상 같은 후보예요.`라고만 설명합니다. 행 순서를 더 좋은 취향으로 표현하지 않습니다.

공유 결과의 반올림된 사용자 점수 또는 이후의 무기 데이터 변경 때문에 `scoreGap < 0`이면 `comparisonStatus`를 `stale`로 둡니다. 이때 후보 간격, 1순위가 된 이유와 2순위의 장점은 만들지 않고 `공유된 뒤 기준값이 조정되어 당시의 순위 차이는 다시 설명하기 어려워요.`라고 안내합니다. 저장된 1~3순위 자체는 기존 공유 정책대로 바꾸지 않으며, 1순위의 잘 맞는 점과 낯설 수 있는 점만 현재 값으로 보여 줍니다.

### 낯설 수 있는 점과 2순위의 장점

1순위에서 불일치가 가장 큰 축 하나를 `caution` 후보로 고릅니다. 같은 값이면 `AXIS_IDS` 순서를 사용합니다.

- `mismatch <= 20`이면 낯설 수 있는 점을 표시하지 않습니다.
- `mismatch > 20`이면 ‘단점’이나 ‘약점’ 대신 `처음에는 이런 점이 낯설 수 있어요`로 표현합니다.

2순위가 더 가까운 축은 다음 값으로 찾습니다.

```text
tradeoff_a = winnerMismatch_a - runnerUpMismatch_a
```

`tradeoff_a >= 5`인 축 중 가장 큰 하나만 고릅니다. 이 축이 `caution`과 같으면 두 문장을 반복하지 않고 `다만 이 기준은 2순위인 <무기>가 더 가깝습니다.`를 같은 문단에 붙입니다. 5보다 작으면 2순위의 장점은 따로 표시하지 않습니다.

## 축별 문장 기준

문장에는 게임 지식을 전제하는 기술명과 내부 변수명을 쓰지 않습니다. 아래 문장은 기본 틀이며, 무기 값이 사용자보다 높은지 낮은지에 따라 방향을 고릅니다.

| 축 | 가까울 때 | 무기 값이 높아 멀 때 | 무기 값이 낮아 멀 때 |
| --- | --- | --- | --- |
| 한방(`attack`) | 대미지를 한 번에 집중하는 정도가 취향과 가깝습니다. | 원하는 것보다 한 번의 기회에 대미지를 더 집중합니다. | 원하는 것보다 대미지를 여러 번 나누어 쌓습니다. |
| 자유(`freedom`) | 행동을 바꾸는 속도가 원하는 정도와 가깝습니다. | 원하는 것보다 행동을 더 빠르고 자유롭게 바꿀 수 있습니다. | 공격 중 다음 행동으로 넘어가는 속도가 원하는 것보다 답답할 수 있습니다. |
| 복잡(`complexity`) | 상황에 맞는 행동을 고르는 정도가 취향과 가깝습니다. | 원하는 것보다 상황에 맞춰 골라야 할 행동이 많습니다. | 원하는 것보다 단순하게 느껴질 수 있습니다. |
| 관리(`management`) | 전투 중 관리해야 하는 정도가 취향과 가깝습니다. | 원하는 것보다 확인하고 관리해야 할 상태가 많습니다. | 원하는 것보다 관리할 요소가 적게 느껴질 수 있습니다. |
| 반격(`counter`) | 받아치는 플레이의 비중이 취향과 가깝습니다. | 원하는 것보다 받아치는 플레이의 비중이 높습니다. | 원하는 만큼 받아치는 플레이가 중심적이지 않을 수 있습니다. |

비교 문장에서는 같은 의미를 길게 반복하지 않고 축의 짧은 표기인 한방·자유·복잡·관리·반격을 사용합니다. 예: `대검보다 한방과 관리 기준에서 더 가까워 1순위가 됐어요.`

## 예시 검산

사용자 점수가 한방 73·자유 21·복잡 57·관리 56·반격 23이고 1순위 건랜스 85.4, 2순위 대검 84.5인 기존 검산 예시를 사용합니다.

| 축 | 건랜스 불일치 | 대검 불일치 | 건랜스의 상대 우위 |
| --- | ---: | ---: | ---: |
| 한방 | 7 | 27 | 20 |
| 자유 | 7 | 4.5 | -2.5 |
| 복잡 | 13 | 13.5 | 0.5 |
| 관리 | 14 | 25.5 | 11.5 |
| 반격 | 32 | 7 | -25 |

예상 표시 문구는 다음과 같습니다.

> **왜 이 무기인가요?**  
> 건랜스와 대검은 거의 비슷한 후보예요.  
> 건랜스는 한방 성향과 행동을 바꾸는 속도가 취향과 가깝습니다.  
> 대검보다 한방과 관리 기준에서 특히 더 가까웠지만, 전체 점수 차이는 작아 근소하게 1순위가 됐어요.  
> 다만 원하는 것보다 받아치는 플레이의 비중이 높아 처음에는 낯설 수 있어요. 이 기준은 2순위인 대검이 더 가깝습니다.

이 예시는 문장 생성 규칙의 회귀 테스트에도 사용합니다. 점수와 문구를 맞추기 위해 무기 데이터를 별도로 바꾸지 않습니다.

## 예외 처리

- 측정된 축이 하나도 없으면 추천 이유 모델은 `null`을 반환하고 영역을 표시하지 않습니다.
- 2순위가 없으면 후보 간격·1순위 비교·2순위 장점은 생략하고 잘 맞는 점과 낯설 수 있는 점만 표시합니다.
- 미측정 축은 가까운 점, 상대 우위, 낯설 수 있는 점에서 모두 제외합니다.
- 공유 결과에서는 링크가 가진 1·2순위를 그대로 `winner`와 `runnerUp`으로 사용하고, 링크의 사용자 축 값과 현재 무기 데이터로 축별 상세값만 계산합니다. 현재 데이터로 순위를 다시 정해 설명 대상을 바꾸지 않습니다. 현재 계산이 저장된 순서와 반대이면 `stale` 규칙을 적용합니다.
- 기존 공유 링크처럼 이름이 없으면 현재 규칙대로 `헌터`를 사용합니다.
- 알 수 없는 무기나 잘못된 공유 코드는 기존 라우팅 검증을 따르며 추천 이유 함수가 오류 화면을 대신 처리하지 않습니다.
- 내부 계산값은 문장 선택에만 쓰고 첫 버전 화면에는 원시 점수 차이와 불일치 숫자를 노출하지 않습니다.

## 구현 순서

Claude Code는 다음 순서로 구현합니다.

1. `src/core/recommend.js`가 축별 불일치 상세값을 한 번만 계산해 순위와 이유에서 공유하도록 확장합니다.
2. 기존 추천 순위 테스트를 먼저 통과시켜 점수·순위가 바뀌지 않았음을 확인합니다.
3. `src/core/reason.js`와 `src/core/reason-copy.js`를 만들고 선택 규칙을 순수 함수로 구현합니다.
4. `src/app.js`에서 정상 결과와 공유 결과의 1·2순위로 이유 모델을 만듭니다.
5. `src/ui/views.js`에 `renderRecommendationReason(reason, weapons)`를 추가하고 순위 아래·차트 위에 렌더링합니다.
6. 기존 스타일 체계에 맞춰 모바일 한 열, 충분한 대비와 제목 구조를 적용합니다.
7. 단위 테스트와 화면 테스트를 추가한 뒤 `npm test`와 `npm run build`를 실행합니다.
8. 구현이 끝나면 이 문서의 상태, README, 검사 설계, 개발 문서와 결정 기록을 ‘구현 완료’로 갱신합니다.

## 필수 테스트와 완료 조건

- 같은 사용자 점수·무기 데이터·1·2순위는 항상 같은 이유 모델과 문구를 만듭니다.
- 이유에 선택된 불일치는 `AXIS_MISMATCH`로 계산한 값과 정확히 같습니다.
- 이 기능 추가 전후의 14개 무기 점수와 순위가 모두 같습니다.
- 가까운 점은 최대 2개, 상대 우위는 최대 2개, 낯설 수 있는 점은 최대 1개만 표시합니다.
- 점수 차이 2와 5, 불일치 10·20·30, 비교 차이 5의 경계값을 테스트합니다.
- 최종 점수 동점, 최대 불일치 동점, 미측정 축, 2순위 없음, 측정 축 없음의 결과를 테스트합니다.
- 낯설 수 있는 축과 2순위가 더 가까운 축이 같아도 같은 설명을 두 번 표시하지 않습니다.
- 다른 순위 무기를 선택해도 1순위 추천 이유는 바뀌지 않고 차트·소개·영상만 바뀝니다.
- 정상 결과와 같은 프로필·같은 1·2순위를 가진 공유 결과는 같은 이유를 표시합니다. 반올림이나 데이터 변경으로 저장된 순서와 현재 계산이 반대인 공유 결과는 `stale` 안내와 1순위 자체의 설명만 표시합니다.
- 무기 이름 등 표시 데이터에 HTML 특수 문자가 있어도 마크업으로 실행되지 않습니다.
- 좁은 화면과 키보드 탐색에서 기존 순위 선택·나머지 무기·공유 동작이 깨지지 않습니다.

## 첫 버전에서 하지 않는 것

- 실행 중 생성형 AI로 문구 만들기
- 추천 이유 전용 시트 열 추가
- 적합도를 확률·정확도·백분율로 표시
- 14개 무기 각각의 동적 추천 이유 제공
- 추천 이유를 공유 이미지에 포함
- 사용자 테스트 전 임계값을 자동 학습하거나 개인별로 변경
