# MonBTI — 몬BTI

몬스터헌터 입문자가 자신의 플레이 취향에 맞는 무기를 찾도록 돕는 웹 검사입니다.
MBTI 검사처럼 질문에 답하는 경험을 제공하며, 기존 유저에게는 자신의 취향을 돌아보고 즐길 수 있는 콘텐츠를 목표로 합니다.

## 프로젝트 방향

- **첫 화면:** 작품 로고로 기준 작품을 선택한 뒤 해당 작품의 검사로 진입합니다. 작품 카드 아래의 ‘검사 설명’에서 검사 대상과 기준을 쉬운 말로 안내합니다.
- **현재 지원 범위:** 몬스터헌터 와일즈만 대상으로 합니다.
- **주요 대상과 목적:** 입문자의 무기 선택을 돕습니다. 질문과 설명은 게임 지식이 없어도 이해할 수 있게 작성합니다.
- **질문 방향:** 자신의 게임 스타일을 이미 알고 있다고 가정하지 않습니다. 게임 용어 없이 한 호흡으로 읽히는 짧은 일상 문장으로, 심리테스트처럼 바로 떠오르는 선호를 간접적으로 묻습니다. 한 응답은 여러 축으로 해석할 수 있지만, 독립된 주장들을 묶어 답하기 어렵게 만들지 않습니다. 앞으로 문항 작성·검토는 [질문 작성 가이드](docs/question-guide.md)를 따릅니다.
- **기존 유저:** 검사와 결과를 재미있게 즐길 수 있도록 구성합니다.
- **배포 목표:** GitHub Pages에서 이용할 수 있는 웹사이트입니다.
- **개발 도구:** Codex와 Claude Code로 작업하며, 공통 지침과 기획을 저장소에서 관리합니다.

현재는 작품 선택 → 질문 응답 → 결과 확인까지 동작하며, 무기 선택 기준 다섯 가지를 정했습니다.
결과 화면은 1~3순위 무기(1순위 강조, 무기 아이콘), 나와 무기의 기준을 함께 그린 오각형 방사형 차트, 무기 소개 영상, 이미지·링크 공유로 구성합니다.
무기 추천은 사용자 축 점수와 무기 특성값의 축별 적합도를 평균해 1~3순위를 정하며, 사이트에 구현되어 있습니다.
응답은 모든 질문에 공통인 1~6단계 동의 척도를 사용하며, 한 질문이 여러 축에 영향을 줄 수 있습니다. 질문은 검사마다 무작위 순서로 표시합니다.
질문 수와 유형 구조는 미정이며, 확정한 추천 공식은 [검사 설계](docs/test-design.md)에 기록합니다.
기술 스택은 GitHub Pages에 맞는 Vite 기반 정적 웹사이트로 정했습니다.
참고 자료의 분류 체계를 어느 범위까지 채택할지도 자료 검토 후 결정합니다.

## 무기 선택 기준

멋짐 등 주관적인 인상보다 입문자의 손에 익숙해질 수 있는 플레이 특성을 기준으로 삼습니다.

| 기준 | 영문명·필드 이름 | 의미 |
| --- | --- | --- |
| 대미지 집중도 | attack | 자주 대미지를 누적하는 지속형 ↔ 준비한 기회에 큰 대미지를 집중하는 한방형 |
| 자유도 | freedom | 행동을 시작한 뒤 마음을 바꿨을 때 공격·이동·방향·회피·가드 등 원하는 다음 행동으로 빠르게 전환할 수 있는 정도 |
| 운용 복잡도 | complexity | 상황에 맞는 행동·파생·상태 전환을 골라야 제 역할을 하는 정도 |
| 관리 부담 | management | 전투 중 무기 고유 자원·게이지·강화 상태·지속 시간 등을 꾸준히 확인하고 유지·소비·보충해야 하는 정도 |
| 카운터 취향 | counter | 몬스터의 행동을 기다렸다 정확한 때에 받아치는 플레이가 얼마나 중심인가 |

`attack`은 내부 필드명이며 화면에는 이해하기 쉬운 **한방**으로 표시합니다. 공격 속도가 아니라 대미지 보상의 분배 방식을 뜻합니다. 운용 복잡도는 콤보나 기술의 개수가 아니라 제 역할을 위해 상황에 맞는 선택을 요구하는 정도이며, 관리 부담은 무언가를 모으거나 일반적으로 정리하는 성향을 뜻하지 않습니다.
대미지 집중도와 카운터 취향은 사용자 성향과 무기 특성의 절대 차이를 보고, 자유도는 사용자가 원하는 최소 수준보다 무기가 부족한지를 평가합니다. 운용 복잡도와 관리 부담은 양쪽 차이를 모두 보되, 무기가 사용자보다 높은 초과 부담은 100%, 낮은 쪽의 차이는 50%만 반영합니다.
자유도는 단순 이동 속도나 공격 속도가 아니라 **입력한 의도를 캐릭터가 얼마나 빨리 따라주는가**를 봅니다. 무기 값은 위기 전환성 35%, 공격 즉응성 25%, 방향·위치 수정 25%, 행동 단위 15%를 가중 합산하고 5점 단위로 반올림합니다. 일반 회피와 가드는 위기 전환으로 인정하지만 카운터 성공 보상은 `counter`에서, 운용 선택과 파생을 익히는 부담은 `complexity`에서 따로 평가합니다.
`counter`는 사용자에게는 카운터 플레이의 선호도, 무기에는 카운터가 운용의 정체성에서 차지하는 중심도를 뜻합니다. 낮은 사용자 값은 카운터 자체를 싫어한다기보다 먼저 흐름을 만들거나 카운터가 필수가 아닌 플레이를 더 선호한다는 뜻입니다.
결과 화면과 차트에서는 다섯 기준을 순서대로 **한방·자유·복잡·관리·반격**으로 짧게 표기합니다.
세부 평가 범위는 [검사 설계](docs/test-design.md)에 기록합니다.

## 데이터 원본

무기 특성과 질문은 [MonBTI_테이블](https://docs.google.com/spreadsheets/d/124oQusXZQ6_F9-UYUVAzG3TD7u50oBjKdBIEbrT7Ras/edit)에서 관리합니다.
와일즈 데이터는 `Wilds_Weapon`과 `Wilds_Question` 탭을 사용합니다.
질문은 한 행에 ID·순서·문구와 다섯 축의 부호 있는 가중치를 기록합니다. 응답 1~6에 각각 -1·-0.6·-0.2·0.2·0.6·1을 곱해 축별로 합산합니다. 음수 가중치는 방향을 반대로 바꾸며, 0·빈칸은 해당 축에 영향을 주지 않습니다.
축별 합산값은 해당 축의 가중치 절댓값 합으로 나누어 0~100 사용자 점수로 환산합니다. `attack`·`counter`는 사용자와 무기의 절대 차이, `freedom`은 사용자가 원하는 자유도보다 무기가 부족한 값으로 불일치를 계산합니다. `complexity`·`management`는 무기 값이 사용자보다 높으면 차이 전부, 낮으면 차이의 절반을 불일치로 반영합니다. 다섯 축 적합도의 평균으로 무기를 정렬합니다.
무기 기준값 입력 범위는 0~100이며, 질문 가중치는 -100~100입니다. 무기 값과 질문 문항은 원본 시트에서 계속 조정합니다.
사이트는 시트에서 내보낸 데이터를 검증·변환한 JSON을 배포에 포함하는 방식으로 개발합니다.
열 정의와 반영 절차는 [시트 데이터 설계](docs/data-schema.md)에 기록했습니다.
시트 편집 후 [Actions → 시트 데이터 갱신](https://github.com/PieceOfPaper/MonBTI/actions/workflows/refresh-data.yml)에서 **Run workflow → main → Run workflow**를 누르면 검증·JSON 갱신·데이터 커밋·Pages 배포까지 실행합니다. 별도의 입력값이나 인증 Secret은 필요하지 않습니다.
로컬에서는 `npm run data:convert`로 같은 변환기를 실행할 수 있습니다.

## 빠른 시작

Node.js 22 이상에서 다음 명령을 실행합니다.

```sh
npm install
npm run dev
```

검증과 배포 절차는 [개발 및 AI 협업](docs/development.md)에서 확인합니다.

## 문서 갱신 원칙

대화에서 정리한 내용은 사용자가 저장소 반영을 명시적으로 요청했을 때만 기록합니다.
반영을 요청받은 방향 변경은 같은 작업에서 README와 관련 기획서를 함께 수정합니다.
변경 이유와 영향을 [결정 기록](docs/decisions.md)에 남깁니다.
제안과 미정 항목을 확정된 요구사항처럼 기록하지 않습니다.
